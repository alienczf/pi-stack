## Finding

- **No hook API.** Stock v0.10.1 has no user-configurable hook, plugin or script that runs before or after compaction. `git grep` for pre/post/before/after/on-compact and for any settings-level hooks config finds none. The only callback "hooks" are internal Rust traits (provider stream hooks, cron scheduler hooks).
- **Settings.** `crates/pa-core/src/settings/types.rs:103-111` has `CompactionSettings` with only `enabled`, `thresholdPercent`, `reserveTokens`, `keepRecentTokens` and `agentCallable`. There's no instructions or prompt field. The summarizer prompt is a hard-coded constant: `crates/pa-core/src/session_engine/compaction.rs:455` (`SUMMARIZATION_PROMPT`), with `:463` for the update variant.
- **Before compaction: notification only, not a hook.** `crates/pa-daemon/src/auto_compaction.rs:72-117`: once the threshold is due, the engine emits `compaction_start` with reason `threshold` and then starts the summarizer straight away (`engine.session.compact(None, …)`, so the threshold path gets no custom instructions). Nothing waits for a client. The emit callback's `false` return only cancels the turn in process. An attached client sees the event because the supervisor forwards it (`crates/pa-daemon/src/supervisor/supervision.rs:817-845`). By then, though, the summarizer is already running. The client's only lever is `abort_compaction` (`crates/pa-types/src/daemon/command.rs:990-996`), which races the summarizer. So nothing can run a save-STATE turn before stock automatic compaction starts.
- **After compaction: a usable signal.** On success the engine emits `compaction_end` (reason `threshold`) together with the saved compaction entry (`auto_compaction.rs:167-174`). Skip, cancel and failure each emit their own `compaction_end` (`:180-200`). The supervisor forwards and journals it (`supervision.rs:846-860`). A connected pi-stack client can act on it, for example by sending a resume message. If the client is disconnected it misses the event, because old cursors return `event_replay_not_available`. In that case the compaction entry in the session file is the fallback.
- **The other automatic path.** Overflow recovery (`crates/pa-daemon/src/overflow_compaction.rs:1-4`) also compacts automatically, but only when compaction is enabled or a compaction is already scheduled (`:191-196`).
- **Switching it off.** `compaction.enabled=false` turns off both the threshold path and the overflow path. Per 42 §3, it has to be in settings before the session is built: the supervisor command `set_auto_compaction` (`command.rs:952-959`) does not update a core session that already exists.
- **What we can build on.** Two stock pieces support rolling our own:
  - direct `compact{activeSessionId, customInstructions}` (`command.rs:968-976`);
  - the agent-callable `compact.status` (tokens, context_window, percent, scheduled) and `compact.run` (schedule a compaction with instructions for the next turn boundary). These are in `crates/pa-core/src/session_engine/turn_boundary.rs:1-4,212-260` and are registered when `agentCallable` is unset or true (`session_engine/engine.rs:369-371`). Scheduled runs emit `compaction_start` with reason `requested` (`crates/pa-daemon/src/agent_engine/turn/boundary.rs:64-84`).

## Consequence under Z25 answer 4

There's an after-compaction hook (the `compaction_end` event) but no before-compaction hook. ZF's condition therefore applies: switch off stock automatic compaction (`compaction.enabled=false` before the session is built) and run our own percentage check, then save, compact and resume. The percentage figure can come from stock `compact.status` or the context usage in session state, and the compact step uses direct `compact`.

The design still has to decide when that check runs (for example at idle boundaries driven by the tick, or by the agent calling `compact.status` and `compact.run`), and what happens on overflow while automatic compaction is off. The overflow arm then no longer compacts, and the turn fails with the stock overflow error.
